# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repository is a single self-contained static page: [index.html](index.html) — a self-publishing / author-services landing page ("Mindluma Collective"). There is no build step, no package manager, no bundler, and no test suite. All HTML, CSS (in a `<style>` block), and JavaScript (in a `<script>` block) live in that one file. The only external dependency is the Google Fonts CDN (Fraunces + Inter). `robots.txt` and `sitemap.xml` sit alongside it at the repo root for basic technical SEO — they reference the placeholder domain `https://www.mindlumacollective.com/` and should be updated once a real domain is live (same goes for the `og:image`/`twitter:image` URLs in `<head>`, which point at a not-yet-uploaded `/og-image.jpg`).

## Working with this file

- There is no build/lint/test command — the site is opened directly in a browser (`Start-Process index.html` on Windows, or double-click). Because the page fetches Google Fonts and uses `file://`-unfriendly patterns in some tooling, prefer serving it over `http://localhost` (e.g. a throwaway `node -e "require('http')..."` static server) when testing with a browser automation tool.
- Preserve the single-file structure: CSS stays inline in `<style>`, JS stays inline in `<script>`, no external frameworks or build tooling should be introduced unless explicitly requested.
- CSS uses custom properties defined in `:root` for the palette (`--color-ink`, `--color-ink-soft`, `--color-paper`, `--color-white`, `--color-off-white`, `--color-lime`, `--color-lime-text`, `--color-lime-soft`, `--color-grey`) and a spacing scale (`--space-1` through `--space-9`). Reuse these tokens rather than hardcoding new values. `--color-lime` (bright) is for dark backgrounds/icon chips/large elements; `--color-lime-text` (deep olive) is the accessible variant for text/links on light backgrounds — bright lime fails WCAG contrast as body/label text on the paper/white sections.
- Section anchors (`#services`, `#process`, `#roadmap`, `#testimonials`, `#contact`) are used by both the nav links and in-page CTAs — keep `id`s and hrefs in sync if sections are renamed or reordered.
- The JS is wrapped in a single IIFE at the bottom of the file, organized into clearly commented blocks (sticky nav, mobile hamburger, scroll-reveal via `IntersectionObserver`, hero stat counters, testimonial carousel dots, shared field-error helpers, lead-magnet form, enquiry form, footer year). Keep new behavior in this same pattern rather than adding separate script tags.
- `prefers-reduced-motion` is respected in both CSS (media query disabling the hero gradient animation, the hero-shelf/book-mock float animations, and `.reveal` transitions) and JS (skipping counter/scroll animations) — any new animation should follow the same guard.
- There are two forms, both client-side-only validation that simulate submission with `setTimeout` — there is no backend: the lead-magnet opt-in (`#roadmap-form`, first name + email, delivers "the roadmap") and the consultation enquiry (`#enquiry-form`, fuller project details). They share the `showFieldError`/`clearFieldError` helpers but keep separate `requiredFields` arrays and submit handlers — don't merge them into one abstraction. Success panels are built with DOM APIs (`createElement`/`textContent`), not `innerHTML` string interpolation, since form values are user-supplied — keep that pattern for any similar dynamic content to avoid introducing an XSS vector.
- No `localStorage`/`sessionStorage` is used; don't introduce it without checking with the user first, per the original build constraints for this page.
- Contact details (address, email, phone) are intentionally realistic-looking placeholders, not real business info — swap them before this goes live, along with the canonical/OG URLs and the JSON-LD `ProfessionalService` block in `<head>`.
